# 测试规范

本文件约束**怎么写断言**。跑哪些脚本见 [README](../README.md#测试与验证) 与
[项目规则](../.trae/rules/project_rules.md#5-端到端回归)。

命令清单会告诉你"跑什么"，本文件告诉你"结果说明了什么" —— 后者才是测试失效的
主要来源。一个跑绿但没有诊断能力的测试套件，比没有测试更危险：它让人停止怀疑。

---

## 三条核心准则

### 1. 改契约前先看谁在依赖它，并判断契约本身对不对

测试红的时候，先分清是**实现错了**还是**契约错了**。

契约错了才改测试，而且要在 review 里写明**为什么这次判定为契约错**。否则
「改测试让它变绿」会变成肌肉记忆，等于亲手拆掉回归网。

**本项目的实例**：`thumbs` 字段有 share.jpg 时只返回 1 张。实现画廊大图查看时，
最省事的做法是让 `thumbs` 返回全部产物 —— 但 `verify-share-card.mjs` 与
`verify-decorate-persist.mjs` 断言的「卡片只显示最有代表性的那张」**本身是对的**。
所以正确解法是新增 `media` 字段，而非改 `thumbs`。

> 新增而非修改，好处不只是省事：两个字段并存后，
> 「`thumbs=1` 但 `media=6`」这个对照本身成了护栏 —— 谁把两者改混都会红。
> **好的数据结构能自我防守。**

判断契约对不对的方法：**问"这个约定在功能上合理吗"，而不是"测试当时为什么这么写"。**
测试是契约的**记录**，不是契约的**来源**。

### 2. 断言钉不变量，不钉当前取值；别吞异常

#### 2.1 禁止硬编码数量

```js
check("位图素材工具条出现 8 项", (await btns.count()) === 8);  // ❌
```

素材库是活的 —— 加一条登记表就多一张贴纸，而**"多了一张贴纸"是正常功能变更**，
不该让测试变红。

误报多了，团队就会习惯性忽略这条红灯。等它真正红的时候，人已经不看了 ——
这比没有测试更糟，因为灯还亮着。

```js
const expected = await readManifestKeys();                    // ✅
check("素材项与 manifest 一一对应",
  shownKeys.length === expected.length && expected.every((k, i) => k === shownKeys[i]));
```

守住的**不变量**是"工具条展示的东西 = manifest 登记的东西"，这条不随素材增减而失效。

> 同理适用于形状数量、按钮数量、数组长度。`== 8` 和 `== manifest.length`
> 看起来只差几个字符，前者会在三个月后变成噪音。

#### 2.2 禁止吞掉超时

```js
await row.waitFor({ timeout: 10000 }).catch(() => null);   // ❌
const n = await row.count();   // 组件压根没渲染 → 报 "got 0"
```

上面两行的问题是**诊断信息被销毁**：没渲染报的是"数量不对"，排障方向直接被带偏
—— 去查数量，而真正原因是组件没挂上。

```js
const appeared = await row.waitFor({ timeout: 10000 })     // ✅
  .then(() => true).catch(() => false);
check("素材工具条已渲染", appeared);      // 缺失
const n = await btns.count();
check("素材项与 manifest 一一对应", ...); // 数量/内容
```

**"整体缺失"与"数量不符"必须是两条独立断言。** 合成一条时，缺失会伪装成数量问题。

要容错就单独写一条断言说明"预期降级"，不要把超时和失败混成同一个 `null`。

#### 2.3 读「不存在」类状态前必须确认系统已稳定

```js
check("manifest 失败时不渲染素材行",
  (await page.locator("[data-sticker-assets]").count()) === 0);  // ❌
```

reload 后 React 可能还没提交完，读到的就是**暂时的 0** —— 断言通过，而功能其实
是坏的。等于没断言。

正确做法：给显式等待，并用**正向断言双侧夹逼**。

```js
await page.waitForTimeout(1200);                            // ✅
check("素材行不渲染", (await page.locator("[data-sticker-assets]").count()) === 0);
// 还要证明编辑器本身没被拖垮:
check("代码形状仍能摆上画布", ink > 500);                   // 正向
```

#### 2.4 只验"有东西"不够，要验位置与尺寸

```js
check("画布上出现贴纸像素", ink > 500);   // ❌ 画到角落也通过
```

落点固定在中心时，像素应当**集中在中心附近**。只验总量的话，贴纸画到角落、
缩得极小、或读到上一次运行的残留帧，都能凑够阈值 —— 而这些恰是坐标算错时最常见
的表现。

返回包围盒并断言位置与尺寸：

```js
return { n, minX, minY, maxX, maxY, w: c.width, h: c.height };
check("贴纸落在点击位置附近", Math.abs(cx - 0.5) < 0.2 && Math.abs(cy - 0.5) < 0.2);
check("贴纸尺寸符合默认 size", boxW > 0.08 && boxW < 0.4);
```

> 断言"非底色像素占比 > 0.5%"这类**相对量**时，选参照物要能排除巧合：
> 纯色帧做输入，色差就只可能来自被测算子，不受画面本身明暗污染。
> 参考 `verify-era-e2e.mjs` —— 中灰帧里顶部与底部的 R 差**只可能**来自 era 漏光。

### 3. 删除操作只删显式清单，绝不按特征扫

**本项目最重要的一条。**

```js
// ❌ 按"单产物"扫全量删除"测试产生的新 job"
const extra = items.filter((x) => x.media.length === 1).map((x) => x.job_id);
for (const id of [jid, ...extra]) await del(id);
```

**单张拍摄是正常使用路径**。这段逻辑跑一次，就会把用户的照片清掉 ——
而且它不会报错，会"成功"。

```js
// ✅ 只删本次亲手建的
const createdIds = [jid];
// 新 job 由保存接口返回的 id 追加进来, 不做事后反推
createdIds.push(newJob.job_id);

for (const id of createdIds) await del(id);
```

核心原则：**「按特征推断哪些是我造的」这个假设，在真实用户数据面前不成立。**

凡是 `delete` / 扫全量 / 按条件批量操作，必须有显式的、自己维护的清单。
"事后反推"（跑完再找符合特征的删掉）在这里等价于"按特征扫"。

> 同一条适用于非测试代码：任何 `rm -rf` 式操作都要能回答"它凭什么认为这个该删"。

## 补充：容易被静默跳过的退化路径

**共享命名空间里的 key 撞名，症状是完全静默的。**

本项目的贴纸工具名共用一个 `string` 命名空间（有意省一层 `{kind, key}` 结构体）。
素材 key 一旦与内置形状 key 撞名，该素材会**静默变回代码形状**：

- 按钮在，数量不变
- lint 不报，TS 不报
- 数量断言照过

只是一张永远摆不出来的图。肉眼和数量断言都发现不了，只能靠专门的撞名检测：

```js
const collided = shownKeys.filter((k) => shapeKeys.includes(k));
check("素材 key 不与内置形状 key 冲突", collided.length === 0, collided.join(","));
```

**省掉的那层结构体，代价是丧失了一个维度上的可检测性。** 简化是有代价的，
账单延后支付。真要简化，就把「唯一性」作为新的不变量显式测出来。

同类需要显式钉住的退化路径：
- 加载失败降级后是否静默隐藏了某个项（导致 `.first()` 选中的是另一个）
- 空数组 / 单元素数组时是否走了不同分支
- 排序：`photo_10` 会不会排在 `photo_2` 前面（字典序 vs 数字序）

## 补充：lint 报 unnecessary 时多问一句

```
eslint: 'assetImageCount' is an unnecessary dependency
```

不要直接删就完事。**塞进依赖数组却不被回调体读取的东西，下一个人删掉它时
lint 不会报警**，而功能会静默退化。

这里是把变量当"重跑信号"塞进 `useCallback` 依赖数组 —— 依赖数组只能表达
"输入 → 输出"的因果关系，不能用来触发副作用。改成独立 `effect`，让因果写在明面上。

**通用判据**：lint 报 unnecessary 时，顺手问"我为什么想让它在这儿"。
答案通常说明我用了隐式因果关系，而它本该显式。

## 补充：视觉类资产只能靠看

代码层面合理的参数，渲染出来可能是错的。

**实例**：半透明和纸胶带加白色模切边 —— 8 张素材里 7 张都需要白边，
代码完全自洽。但白边把半透明斜纹切碎，胶带像被撕过的。

同类：音符符头最初是扁平平行四边形，读代码时它就是"音符"，画出来才发现不像。

所以：

- 素材生成后**必须目视检查每一张**，不能只看脚本跑通。
- 结论写进脚本注释（本项目：`washi_tape` 不描边），让下一个改脚本的人不会重犯。
- **但注释只能传播结论，替代不了这次亲眼看一遍。**

## 检查清单

写完 / 改完一个测试脚本，逐条过：

- [ ] 没有硬编码的数量断言（除非该数量本身是被测契约，如 `MAX_PHOTOS = 8`）
- [ ] 没有 `.catch(() => null)` 吞超时
- [ ] "整体缺失"与"数量/内容不符"是分开的断言
- [ ] 读「不存在」状态前有等待，且有正向断言双侧夹逼
- [ ] 像素类断言验了位置/尺寸，不只验总量
- [ ] 容错用例验证的是**降级可用**，不只是"不崩"
- [ ] 清理只删显式清单，无按特征扫全量
- [ ] 共享命名空间加了撞名检测
- [ ] 新素材的缩略图真的解码成功（不只是 `<img>` 渲染出来了）
- [ ] 新增/修改后跑过**全量**脚本，而非只跑自己那个

最后一条尤其重要：新功能常共用旧模块（本次的 `burnStickers` 从
`DecoratePage` 私有函数抽成共享模块）。只跑自己的脚本，改坏的是别人的路径。
